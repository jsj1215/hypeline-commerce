# 재고 동시성 — baseline

## 전제

드롭이 열리는 순간 수만 건의 구매 요청이 **인기 SKU 단 하나의 재고 행**으로 향한다.
API 인스턴스를 10대로 늘려도 이 지점은 나뉘지 않는다. 스케일아웃으로 풀리지 않는 병목이다.

이 문서는 그 병목을 DB 만으로 다뤘을 때의 기준선을 기록한다.
Redis 도입은 다음 단계이며, 여기서 나온 수치가 그 근거가 된다.

## 결정 1 — 재고를 SKU 와 다른 테이블로 뗀다

```
sku         id, product_id, sku_code, size, color, additional_price, status   (거의 안 변함)
sku_stock   sku_id, quantity, version                                          (초당 수천 번 갱신)
```

같은 행에 두면 재고를 차감할 때마다 상품명·가격이 함께 든 넓은 행에 락이 걸린다.
재고만 든 좁은 행으로 떼면 락이 걸리는 범위가 줄고, 나중에 이 테이블만 따로 다룰 수 있다.

## 결정 2 — 판단을 애플리케이션이 아니라 WHERE 절에서 한다

```sql
UPDATE sku_stock
   SET quantity = quantity - :qty
 WHERE sku_id = :skuId
   AND quantity >= :qty        -- 이 줄이 핵심이다
```

`quantity >= :qty` 를 WHERE 에 두면 **재고가 충분한지 판단하는 일과 차감하는 일이 한 문장 안에서**
일어난다. DB 가 행 락을 쥔 채로 둘을 함께 처리하므로 그 사이에 다른 트랜잭션이 끼어들 수 없다.

영향받은 행이 0이면 재고가 부족했다는 뜻이다.

### 다른 방식과 비교

| 방식 | 초과 판매 | 비용 |
|---|---|---|
| 조회 후 판단 → UPDATE | **발생** | — |
| `SELECT ... FOR UPDATE` | 안 남 | 락을 애플리케이션 왕복 동안 붙든다 |
| 낙관적 락 (`@Version`) | 안 남 | 경합이 심하면 재시도가 폭증한다 |
| **조건부 UPDATE** | **안 남** | 락 보유가 UPDATE 한 문장으로 짧다 |

드롭처럼 수만 건이 같은 행을 노리는 상황에서 낙관적 락은 특히 나쁘다.
대부분의 요청이 버전 충돌로 튕겨 재시도하면서 부하가 오히려 증폭된다.
`@Version` 컬럼은 두되 재고 차감에는 쓰지 않는다. 관리자 재고 조정처럼 경합이 없는 경로용이다.

## 결정 3 — 차감 트랜잭션을 짧게 유지한다

InnoDB 의 행 락은 **UPDATE 문이 끝날 때가 아니라 트랜잭션이 커밋될 때** 풀린다.
주문 생성이나 PG 호출을 같은 트랜잭션에 넣으면 그 시간 내내 재고 행의 락을 붙들게 되어,
조건부 UPDATE 로 얻은 이점이 사라진다.

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void deduct(Long skuId, long quantity) { ... }
```

`REQUIRES_NEW` 로 분리해 호출하는 쪽이 긴 작업과 묶지 못하게 한다.

## 검증 — 대조군과의 대비

"안전하다"는 주장만으로는 근거가 되지 않는다.
순진한 구현이 실제로 초과 판매를 일으키는 것을 먼저 보이고 조건부 UPDATE 와 대비시켰다.

### 대조군 — 조회 후 판단하고 갱신하는 구현

```
스레드 A: SELECT quantity → 1          스레드 B: SELECT quantity → 1
스레드 A: 1 >= 1 이므로 통과            스레드 B: 1 >= 1 이므로 통과
스레드 A: UPDATE quantity = 0          스레드 B: UPDATE quantity = 0
                                       → 두 명 모두 성공. 재고 1개가 2개 팔렸다
```

### 측정 결과 (Testcontainers MySQL 8.0)

| 구현 | 초기 재고 | 동시 시도 | 팔린 수량 | 잔여 재고 | 판정 |
|---|---|---|---|---|---|
| 대조군 (조회 후 판단) | 10 | 100 | **100** | **8** | 10배 초과 판매, 총량까지 깨짐 |
| 조건부 UPDATE | 100 | 500 | 100 | 0 | 정확 |
| 조건부 UPDATE | 137 | 400 | 137 | 0 | 성공 + 잔여 = 초기 |
| 조건부 UPDATE (2개씩) | 101 | 200 | 100 (50건) | 1 | 남은 1개를 쪼개 팔지 않음 |
| 조건부 UPDATE (차감·복원 혼합) | 100 | 200 | — | 100 | 총량 보존 |

대조군은 재고 10개로 100개를 팔았고, 잔여가 8로 남아 **성공 수량과 잔여의 합이 초기 재고와 맞지 않는다.**
읽기와 쓰기 사이에 끼어든 갱신이 서로를 덮어썼기 때문이다.

### 검증 방식

`CountDownLatch` 로 모든 스레드를 한 지점에 모았다가 동시에 푼다.
스레드를 만들자마자 실행하면 생성 순서대로 늘어져 실제 경합이 재현되지 않는다.

판정은 **최종 상태의 정합**으로 한다.

```
성공 건수 + 잔여 재고 == 초기 재고
```

중간 과정이 어떻게 얽혔든 이 등식이 성립하면 재고가 새지도 늘지도 않은 것이다.

### 테스트 하니스에서 발견한 결함

처음에는 스레드 풀 크기를 `min(threads, 64)` 로 잡고 500개 작업을 제출했다.
64개 작업이 시작 신호를 기다리며 모든 풀 스레드를 점유했고, 나머지 436개는 실행조차 되지 못해
준비 완료 신호가 영원히 오지 않았다.

배리어로 스레드를 모으려면 **풀 크기가 작업 수 이상이어야 한다.**
테스트가 통과하지 못해 드러났지만, 통과했다면 실제로는 64개만 경합한 것을
500개가 경합했다고 잘못 기록할 뻔했다.

## 처리량 한계 실측

정합성은 확보했다. 그 대가로 처리량이 어디서 막히는지를 잰다.
이 수치가 Redis 도입의 근거가 된다.

측정 조건 — 로컬 단일 머신, MySQL 8.0 (Docker), 앱 인스턴스 1대,
`capacity` 프로파일(도착률 100 → 8,000 RPS 계단식 증가), 재고 100만(품절이 나지 않게).

### 결과 — 모든 요청이 같은 SKU 를 노릴 때 (드롭 상황)

| 항목 | 값 |
|---|---|
| 처리량 | **566 RPS** |
| P95 응답 시간 | **8.33초** |
| P99 응답 시간 | 8.48초 |
| 중앙값 | 7.71초 |
| 초과 판매 | **0건** |
| 5xx | **0건** |
| 소화하지 못해 버린 요청 | 257,093건 (목표 도착률의 74%) |

정합성은 완벽하다. 초과 판매도 서버 오류도 없다. 다만 **느리다.**

목표 규모는 피크 50,000 RPS 인데 566 RPS 에서 막힌다. 88배 차이다.
버린 요청이 처리한 요청의 세 배에 가깝다는 것은 이미 한계를 한참 넘겼다는 뜻이다.

### 병목이 어디인지 — 경합을 없앤 대조 측정

느리다는 사실만으로는 원인을 알 수 없다. 앱이 느린 것인지, DB 가 느린 것인지,
아니면 **하나의 행에 몰린 것**이 문제인지 구분해야 한다.

그래서 같은 부하를 SKU 100개로 흩어 다시 쟀다.
요청 수도 앱도 DB 도 그대로이고, 오직 **노리는 행이 하나냐 100개냐**만 다르다.

| 항목 | 같은 SKU 1개 | SKU 100개로 분산 | 차이 |
|---|---|---|---|
| 처리량 | 566 RPS | **1,503 RPS** | 2.7배 |
| P95 | 8.33초 | **2.09초** | 4배 |
| 중앙값 | 7.71초 | 0.84초 | 9배 |
| 버린 요청 | 257,093 | 117,933 | 절반 이하 |
| 초과 판매 | 0건 | 0건 | — |

**앱도 DB 도 요청 수도 같은데 노리는 행의 개수만 바꿨더니 처리량이 2.7배가 되었다.**
병목은 시스템 전반이 아니라 하나의 행에 몰린 것 자체다.

InnoDB 는 같은 행을 갱신하려는 트랜잭션을 행 락으로 줄 세운다.
드롭은 정의상 인기 SKU 하나에 모든 요청이 몰리는 상황이므로, 이 직렬화를 피할 수 없다.

### 이 병목은 스케일아웃으로 풀리지 않는다

API 인스턴스를 10대로 늘려도 결국 같은 행 하나를 두고 줄을 선다.
인스턴스가 늘어나는 만큼 대기열만 길어질 뿐 처리 속도는 그대로다.
오히려 DB 커넥션 경합이 더해져 나빠질 수 있다.

읽기는 리플리카로, 무상태 처리는 인스턴스 증설로 해결되지만
**단일 행에 대한 쓰기 직렬화는 애플리케이션 계층을 늘려서 해결되는 종류의 문제가 아니다.**
차감이 일어나는 자리를 DB 행이 아닌 다른 곳으로 옮겨야 한다.

그것이 다음 단계에서 Redis 를 쓰는 이유다. "빠르니까"가 아니라
**경합 지점을 디스크 기반 행 락에서 인메모리 단일 스레드 연산으로 옮기기 위해서**다.

## 남은 것

- 인스턴스를 늘려도 이 지점이 나아지지 않는다는 확인
- Redis Lua 원자적 차감으로 전환하고 같은 시나리오로 전후 비교

## 범위 밖

대기열, 멱등키, 주문·결제 연결. 이 문서는 재고 차감 원시 연산만 다룬다.
