# Hypeline — 컨셉과 규모

## 무엇을 만드는가

의류 브랜드가 라이브 방송을 켜고, 방송 도중 정해진 시각에 한정 수량 판매(**드롭**)를 여는 커머스다.
시청자는 방송을 보다가 드롭이 열리는 순간 동시에 구매를 시도한다.

판매 단위는 상품이 아니라 **SKU(상품 × 사이즈 × 컬러)** 다.
후드티 한 종을 200장 푼다고 해도 실제로는 `M 블랙 40장`, `L 블랙 60장` 처럼 쪼개져 있고,
인기 사이즈 하나에 경합이 집중된다. 상품 단위로 재고를 잡으면 이 경합이 안 보인다.

일반 커머스와 다른 점은 트래픽의 모양이다.

- **읽기가 한 곳에 몰린다** — 인기 방송 1개에 동시 시청자 수만 명이 붙고, 그들이 전부 같은 방송의 사이즈별 잔여 수량·판매량·댓글을 실시간으로 본다
- **쓰기가 한 순간에 몰린다** — 드롭이 열리는 초에 수만 건의 구매 요청이 인기 SKU 단 하나의 재고 레코드로 향한다
- **두 부하가 동시에 온다** — 실시간 전파를 유지한 채로 쓰기 폭주를 견뎌야 한다

## 왜 이 컨셉인가

인스턴스를 10대 이상 띄우는 것이 **필연이 되는** 도메인이 필요했다.
무상태 HTTP 서버를 늘리는 것만으로 해결되는 부하는 분산 시스템 문제가 아니다.

이 도메인은 스케일아웃 자체가 새로운 문제를 만든다.

| 스케일아웃이 만드는 문제 | 대응 |
|---|---|
| SSE 커넥션이 10대에 흩어져 이벤트가 일부 시청자에게만 도달 | Redis Pub/Sub 로 전 인스턴스 브로드캐스트 |
| 10대가 동시에 같은 SKU 재고를 차감 | Redis Lua 스크립트로 원자적 차감 |
| 재시도·중복 클릭이 10대에 분산되어 중복 주문 | 멱등키를 Redis 에 선점 |
| 주문 커밋과 이벤트 발행이 따로 놀아 집계 유실 | Transactional Outbox |
| 인기 SKU 재고 키가 Redis 단일 샤드로 몰림 | 재고 키 샤딩 |

## 규모 기준

설계와 용량 산정의 기준값이다.

| 항목 | 값 |
|---|---|
| DAU | 500만 |
| 평시 처리량 | 3,000 RPS |
| 드롭 오픈 순간 피크 | 50,000 RPS |
| 동시 시청자 (인기 방송 1개) | 100,000 |
| 동시 SSE 커넥션 (전체) | 300,000 |
| 상품 수 / SKU 수 | 100만 / 500만 |
| 일 주문 수 | 100만 |
| API 인스턴스 | 10~20대 |

### 이 수치를 어떻게 검증하는가

로컬 단일 머신에서 50,000 RPS 를 그대로 재현하는 것은 부하 생성기 쪽이 먼저 죽어서 불가능하다.
그래서 목표 수치를 직접 때리는 대신 아래 순서로 근거를 만든다.

1. **단일 인스턴스 한계 실측** — `capacity` 프로파일로 임계까지 올려 인스턴스당 처리 가능 RPS 와 그 지점의 P95 를 잰다
2. **선형 확장 확인** — 인스턴스를 1 → 2 → 4대로 늘려 처리량이 비례해 늘어나는지 본다
3. **선형으로 늘지 않는 지점 특정** — 인기 SKU 의 재고 키 하나, 그에 대응하는 DB 레코드 하나, Kafka 파티션 수처럼 인스턴스를 늘려도 안 풀리는 병목을 찾는다
4. **그 병목만 따로 개선하고 전후를 비교한다**

3번과 4번이 이 프로젝트의 본체다. 인스턴스를 늘리면 되는 부분은 기술적으로 할 이야기가 없다.

## 핵심 시나리오

### 드롭 구매

```
시청자 ──(1) 대기열 진입──▶ Redis ZSET 순번 발급
       ◀─(2) 순번/예상 대기──
       ──(3) 입장 토큰 + SKU 지정 구매──▶ Redis Lua 원자적 SKU 재고 차감
                                    ├ 실패 → SOLD_OUT
                                    └ 성공 → 주문 생성 + Outbox 적재 (같은 트랜잭션)
                                              │
                                    Outbox Relay ──▶ Kafka
                                                       │
                                            Streamer ──┼─▶ 판매량 집계
                                                       ├─▶ 랭킹 갱신
                                                       └─▶ Redis Pub/Sub ──▶ 전 API 인스턴스 SSE 팬아웃
```

### 실시간 팬아웃

시청자는 `GET /api/v1/shows/{id}/stream` 으로 SSE 커넥션을 연다.
커넥션은 요청을 받은 API 인스턴스에만 존재한다.
판매·재고 변경 이벤트는 Redis Pub/Sub 채널로 발행되고, 모든 API 인스턴스가 구독해
자기가 들고 있는 커넥션에만 흘려보낸다. 스티키 세션이 필요 없다.
