# 상품 조회 API

## 전제

목표 규모가 상품 100만 · SKU 500만이고 트래픽 대부분이 읽기다.
그래서 "동작하는 조회"가 아니라 **데이터가 늘어나도 비용이 늘지 않는 조회**를 목표로 잡았다.

## 결정 1 — 페이징은 offset 이 아니라 커서

`OFFSET 100000 LIMIT 20` 은 앞의 10만 행을 읽고 버린다. 뒤 페이지일수록 선형으로 느려져서
100만 행 규모에서는 쓸 수 없다.

```sql
-- offset: 뒤 페이지일수록 느려진다
ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000

-- cursor: 인덱스 시크 한 번. 페이지 위치와 무관하게 비용이 일정하다
WHERE (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC LIMIT 21
```

정렬 값이 같은 행이 여럿일 수 있으므로 `id` 를 보조 키로 함께 비교한다.
이것이 없으면 동점 구간에서 중복이나 누락이 생긴다.

커서는 `(정렬값, id)` 를 Base64 로 감싼 불투명 문자열로 주고받는다.
클라이언트가 값을 조작하거나 내부 구조에 의존하지 못하게 하기 위해서다.

**대가**: "5페이지로 점프" 를 지원하지 않는다. 무한 스크롤 UI 를 전제한다.

### 커서 정밀도는 컬럼 정밀도 이상이어야 한다

구현 중 테스트가 실제로 잡아낸 결함이다. 237건을 커서로 끝까지 넘겼더니 233건만 읽혔다.

원인은 정밀도 불일치였다. `created_at` 은 `datetime(6)` 으로 마이크로초까지 저장하는데
커서는 밀리초로 잘라서 인코딩하고 있었다.

```
DB    12:00:00.123456   ← 다음 페이지에서 읽어야 할 행
커서  12:00:00.123000   ← 밀리초로 잘린 값

조건: created_at < 커서  →  .123456 < .123000  거짓
      created_at = 커서  →  .123456 = .123000  거짓
                            → 이 행은 어느 페이지에도 나오지 않는다
```

같은 밀리초 안에 다음 행이 들어간 페이지 경계에서만 발생해서, 조용히 한 행씩 사라진다.
에러도 나지 않고 응답도 정상으로 보인다. 전수 순회 테스트가 아니었으면 못 잡았을 결함이다.

시각과 커서 값의 변환을 `ProductCursor` 한 곳으로 모으고 마이크로초까지 보존하도록 고쳤다.
회귀를 막기 위해 두 가지를 테스트로 고정했다.

- 같은 밀리초 안에서 마이크로초만 다른 두 시각이 서로 다른 정렬 값을 갖는지
- `information_schema` 로 `created_at` 의 실제 정밀도가 커서가 감당하는 범위 안인지

## 결정 2 — 응답에 총 개수를 담지 않는다

필터가 걸린 `COUNT(*)` 는 조건에 맞는 행을 전부 세야 한다. 100만 행에서 매 요청마다 세면
목록 조회 자체보다 카운트가 비싸진다.

`hasNext` 만 내려준다. 판단은 요청 개수보다 한 건 더 읽어서(`LIMIT size + 1`) 한다.
별도 쿼리가 없으므로 비용이 사실상 0이다.

## 결정 3 — 인기순은 실시간 판매량으로 정렬하지 않는다

커서 페이징은 **정렬 키가 변하지 않는다**는 전제 위에 선다.

| 정렬 | 키 | 변동성 | 커서 안정성 |
|---|---|---|---|
| 최신순 | `created_at` | 불변 | 안정 |
| 가격순 | `base_price` | 거의 불변 | 안정 |
| 인기순 | 판매량 | **초당 변동** | **깨짐** |

실시간 판매량으로 정렬하면 페이지를 넘기는 사이 순위가 바뀌어 같은 상품이 두 번 나오거나
아예 건너뛰어진다. 그래서 배치가 주기적으로 확정하는 `popularity_score` 컬럼을 두고 그것으로 정렬한다.
갱신 주기 안에서는 값이 고정이므로 커서가 안정적이다.

갱신 파이프라인은 Kafka streamer 도입 시점에 붙인다. 지금은 컬럼과 정렬만 있다.

## 결정 4 — 캐시 경계를 데이터 변동성으로 나눈다

| 데이터 | 변동성 | 캐시 |
|---|---|---|
| 상품명, 브랜드, 카테고리, 이미지, 기본가 | 거의 없음 | 대상 |
| SKU 잔여 재고 | 초당 수천 번 | **제외** |
| 드롭 할인가 | 방송 중 변동 | **제외** |

상품 상세를 통째로 캐시하면 편하지만, 거기에 재고가 섞이는 순간
"품절인데 구매 버튼이 살아 있는" 화면이 나온다. 그래서 **상세 응답에 재고를 담지 않는다.**
재고는 별도 경로로 실시간 조회한다. 이 경계를 지금 그어두지 않으면 나중에 캐시를 넣을 수 없다.

캐시 자체는 이번에 넣지 않았다. 캐시 없는 상태의 수치를 먼저 재고 나서 넣고 전후를 비교한다.

## 결정 5 — 목록은 엔티티가 아니라 DTO 로 투영한다

목록에 브랜드명이 필요한데 엔티티로 받으면 상품 20개마다 브랜드 조회가 20번 나간다.
QueryDSL 로 조인해 `ProductSummary` 로 바로 투영한다.

브랜드와 상품은 서로 다른 애그리거트이므로 엔티티 연관관계(`@ManyToOne`)를 두지 않고
식별자(`brand_id`)로만 참조한다. 조인이 필요한 곳에서 명시적으로 조인한다.

## 인덱스

커서 페이징은 정렬 키와 인덱스 순서가 맞아야 시크가 걸린다. 안 맞으면 커서로 바꾼 의미가 없다.

```
idx_product_latest           (status, created_at, id)
idx_product_brand_latest     (status, brand_id, created_at, id)
idx_product_category_latest  (status, category, created_at, id)
idx_product_price            (status, base_price, id)
idx_product_popularity       (status, popularity_score, id)
idx_sku_product              (product_id, status)
```

## 검증

| 테스트 | 확인하는 것 |
|---|---|
| `ProductCursorTest` | 커서 인코딩/디코딩 왕복, 불투명성, 잘못된 값 거부 |
| `ProductQueryDslRepositoryTest` | 끝까지 넘겨도 중복·누락 없음, 정렬, 필터 |
| `ProductPagingPerformanceTest` | **10만 건에서 첫 페이지 vs 9만 번째 페이지 비교**, 같은 지점 offset 과 비교, `EXPLAIN` 으로 인덱스 사용 확인 |
| `ProductV1ControllerTest` | API 계약, 404/400, 응답에 재고·총개수 없음 |

`ProductPagingPerformanceTest` 가 이 작업의 핵심 근거다.
offset 이었다면 벌어졌을 격차가 커서에서는 벌어지지 않는다는 것을 같은 데이터로 직접 비교한다.

### 측정 결과 (상품 10만 건, 페이지 20건, Testcontainers MySQL 8.0)

| 측정 | 결과 |
|---|---|
| 커서 — 첫 페이지 | 3ms |
| 커서 — 90,000번째 이후 페이지 | 19ms |
| offset — 같은 90,000번째 지점 | 74ms |
| `created_at` 실제 정밀도 | `datetime(6)` |

같은 지점을 읽는 데 offset 이 커서의 **3.2배**가 걸린다.
10만 건에서 이 정도이고, offset 은 데이터가 늘수록 선형으로 나빠지는 반면 커서는 인덱스 시크라
증가폭이 훨씬 완만하다. 목표 규모인 100만 건에서는 격차가 더 벌어진다.

측정 환경이 로컬 단일 머신이라 절대값 자체는 운영 수치가 아니다.
의미가 있는 것은 **같은 조건에서 두 방식을 비교한 상대 차이**다.
